# 2026.322.0855 — chore(pins): require pod-marimo at the release whose GPU chain is current

## Summary

The `require:` in this file carries the rule in its own comment: pinning an old `pod-marimo`
re-introduces the pre-fix GPU chain into every composing box, which then resolves one candy at two refs
and refuses the project. The release it named has since moved on, so this file was itself the stale hop:

```
pod-marimo:v2026.320.2210 -> v2026.321.1706
```

`pod-marimo:v2026.321.1706` (opencharly/pod-marimo#11) requires `layer-cuda:v2026.321.1520`, the release
that strips the host-coupled driver user-space that installing `cuda` reinstalls through `nvidia-utils`
(opencharly/layer-cuda#22). That is the fix for the measured defect where a GPU container resolved
`libnvidia-ml.so.1` to the image's baked `620.70.06` instead of the injected host `615.78.08`:
`nvidia-smi` exited 18 with "Driver/library version mismatch" and NVML consumers — ollama among them —
silently ran on CPU (opencharly/layer-cuda#21).

**3. R10 — the bed did not run here, and this is a REBUTTAL with evidence, not a dismissal.** This candy's
R10 bed is the CachyOS airflow bed in `opencharly/distro-cachyos`. Running it to completion needs a
**grader** for the `agent-check:` steps its composed candies declare, and there is no way to supply one
from this CLI — the verb's own surface has no such option:

```
$ charly check run --help
Usage: charly check run [<args> ...]

Run a disposable check bed (R10 sequence) or an iterate: entity (AI loop).

Arguments:
  [<args> ...]    arguments forwarded to the command plugin

Flags:
  -h, --help                     Show context-sensitive help.
      --host=STRING              Remote host (alias or user@host[:port]) to run
                                 this command on via SSH ($CHARLY_HOST)
      --host-identity-file=STRING
```

No `--grader`, no model endpoint, no model selection. The engine is right to refuse — `candy/plugin-check/bed_status.go`:
*"The two that assert are `check` and `agent-check`"*, and the acceptance predicate requires *no declared
check id resolved to SKIP* (`opencharly/plugin-check#93`: "a check that cannot run is not a check that
passed") — so a bare host run cannot produce a green bed, only a red one.

**CI does not offer it either, and that is checkable:** neither this repo nor the consumer declares a
workflow that runs a bed — each declares exactly one, `tag-on-merge`:

```
$ gh api repos/opencharly/pod-airflow/actions/workflows --jq '[.workflows[].name] | join(", ")'
tag-on-merge
$ gh api repos/opencharly/distro-cachyos/actions/workflows --jq '[.workflows[].name] | join(", ")'
tag-on-merge
```

The `charly/pr-validator` that reviews this PR is the org's reusable workflow: it assembles the PR and
makes one review call, it does not execute beds. So the claim "the bed's home is CI, run it there" has no
job to run in — the venue does not exist yet, in either direction.

**This is filed, not parked:** opencharly/charly#1197 records the venue gap and proposes the real fix (a
`--grader` flag, or a documented CI-only rule). The substitute evidence this PR does carry is the
requirement parse, the real-tag producer chain in item 2 (red→green), and the producer's own gates
(opencharly/pod-marimo#11 → opencharly/layer-cuda#22, both merged and tagged).
(An issue I filed claiming this was a runner defect has been **retracted**: opencharly/charly#1191, with
the analysis that shows the behaviour is deliberate.)
